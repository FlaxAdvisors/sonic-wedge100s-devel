# PWR1014A power sequencer research (GAP-021, Task 1)

Date: 2026-04-09
Hardware: Accton Wedge 100S-32X, BMC 4.1.51, OpenBMC Facebook fork
Target: Extend `wedge100s-bmc-daemon.c` with PWR1014A voltage telemetry

## Summary — BLOCKED

The PWR1014A on this platform **does not return usable PMBus data**. Every
register read from address 0x3A returns `0xFF` (or `0xFFFF` for word reads),
including the mandatory PMBus identity registers. No voltage telemetry is
recoverable from this part, matching the Facebook Wedge100 OpenBMC design
intent — the stock `pwr1014a` driver is a stub that only exposes
`mod_hard_powercycle`.

The Task 1 plan's assumption that the chip is a functioning UCD9090 PMBus
sequencer with 10 monitored rails is **wrong for this platform**. This is not
a Claude-side probe bug; it is a platform-wide limitation.

Recommendation: close GAP-021 as NOT FEASIBLE on the Wedge 100S hardware and
remove it from the P2 plan. Rail voltage telemetry must come from the IR3581/
IR3584 VRMs instead (Task 2 / GAP-022), or from the COM-e power monitor
(already surfaced on BMC hwmon6 / `com_e_driver`).

## Hardware probe results (verified on hardware 2026-04-09)

### Device location

- Bus: **BMC I2C bus 2** (not bus 3 as the plan assumed — the schematic label
  "BMC_I2C_3" is 1-indexed; Linux enumerates the same bus as `i2c-2`)
- Address: **0x3A**
- Driver binding: `i2c:pwr1014a` (OOT Facebook Wedge100 module, loaded)
- Sysfs path: `/sys/bus/i2c/devices/2-003a/`

```text
$ i2cdetect -y 2 (excerpt)
30: -- -- -- -- -- -- -- -- -- -- UU -- -- -- -- --
```

After `echo 2-003a > /sys/bus/i2c/drivers/pwr1014a/unbind`, the address shows
as `3a` (not `UU`), confirming the chip ACKs at its address.

### Stock driver capability (verified on hardware 2026-04-09)

```text
$ ls /sys/bus/i2c/devices/2-003a/
driver  hwmon  mod_hard_powercycle  modalias  name  subsystem  uevent

$ cat /sys/bus/i2c/devices/2-003a/mod_hard_powercycle
0xff

Note:
Writing 0 here will powercycle the entire module (NOT the chassis)
Bit[7:0] @ register 0x12, register value 0xff
```

The stock `pwr1014a` OOT driver exposes **no voltage, current, or temperature
attributes** — only a single `mod_hard_powercycle` control that writes
register 0x12. The hwmon0 subdirectory has no numeric inputs (only `uevent`).

### Raw PMBus probe (verified on hardware 2026-04-09)

Done with `wedge100s-i2c-daemon`, `wedge100s-bmc-daemon`, and `pmon` stopped
on the SONiC host, and with the BMC-side `pwr1014a` driver **unbound** so
i2c-dev could own the address.

| Register | Name | Read type | Value |
|---|---|---|---|
| 0x00 | PAGE | byte | 0xFF |
| 0x20 | VOUT_MODE | byte | 0xFF |
| 0xD0 | MFR_DEVICE (TI UCD-specific) | byte | 0xFF |
| 0xFD | PMBUS_REVISION | byte | 0xFF |
| 0xFC | IC_DEVICE_ID | byte | 0xFF |
| 0x8B | READ_VOUT | byte | 0xFF |
| 0xEC | PMBus alert | byte | 0xFF |
| 0x00 | PAGE | word | 0xFFFF |
| 0x8B | READ_VOUT | word | 0xFFFF |
| (no reg) | Receive-byte | — | 0xFF |

Also tried with `i2cget -y -f 2 0x3a …` before unbinding the driver — same
results. Writing `0x00` to PAGE (`i2cset -y 2 0x3a 0x00 0x00`) succeeded with
no error but reading back still returned `0xFF`.

**Interpretation:** the chip ACKs its I2C address but refuses to return data
for any PMBus register. No `IC_DEVICE_ID` string (which TI UCD9xxx chips
reliably return), no meaningful `VOUT_MODE`, no `NUM_PAGES`. This behavior is
consistent with a PWR1014A that is either (a) not flashed with a PMBus config
and responds only to its custom vendor-specific `mod_hard_powercycle` at
register 0x12, or (b) physically present but held in reset from a PMBus
perspective.

After the probe, daemons were restarted cleanly:

```text
$ sudo systemctl start wedge100s-i2c-daemon wedge100s-bmc-daemon pmon
$ sudo systemctl is-active wedge100s-i2c-daemon wedge100s-bmc-daemon pmon
active
active
active
```

## Why the plan was wrong

1. **Bus number:** the plan said `BMC_I2C_3` → `bus 3`. Hardware shows `2-003a`
   so the correct kernel bus is `i2c-2`. (Not a blocker on its own.)
2. **Driver stack:** the plan assumed a stock `ucd9000`/`pmbus_core` binding
   exposing `inN_input` hwmon files. Kernel 4.1.51 on this BMC has `pmbus` and
   `pmbus_core` loaded but **no `ucd9000.ko`** (not shipped with this BMC
   firmware). The address is owned by the OOT `pwr1014a` stub which only does
   `mod_hard_powercycle`.
3. **PMBus responsiveness:** even after unbinding the stub, the chip returns
   `0xFF` to every PMBus register — there is no PMBus identity to read and no
   voltage data to decode. The plan's VOUT_MODE decode math is moot.
4. **Reference implementation:** neither ONL's `packages/platforms/accton/
   x86-64/wedge100s-32x/` nor any other Wedge100/Wedge100S reference platform
   reads voltages from the PWR1014A. Only the `mod_hard_powercycle` path is
   used in the wild.

## Decision gate — BLOCKED

Following the plan's Step 2 decision gate:

> **Decision gate:** If the device does not respond, or the data is unusable
> (all 0x0000 or 0xFFFF), STOP and report BLOCKED. Do not guess register
> layouts.

All reads are `0xFF`/`0xFFFF`. **Stopping here.** No `wedge100s-bmc-daemon.c`
changes made, no commits to `wedge100s/i2c-bmc-sysfs`, no tests added. The
worktree was created for Task 1 and left in place for Tasks 2, 3, and HW
Task 2 per the plan's "reuse this worktree" instruction.

## Follow-up suggestions

- **Close GAP-021** as NOT FEASIBLE or re-scope it to cover only the
  `mod_hard_powercycle` reset-path exposure (already implemented on BMC; no
  telemetry to surface).
- **GAP-022 (IR3581/IR3584 VRM telemetry)** becomes the only voltage
  telemetry path for the core rails. Task 2 needs its own independent
  hardware probe before coding.
- **COM-e rails** (CPU Vcore, +3V, +5V, +12V, VDIMM) are already available on
  the BMC's `com_e_driver` hwmon (`hwmon6/in[0-4]_input`). A future small
  task could surface these through `wedge100s-bmc-daemon` into
  `/run/wedge100s/vrail_*_mv` without touching the broken PWR1014A path.
- The pwr1014a OOT driver source lives in the OpenBMC Facebook-Wedge100 tree
  (`meta-facebook/meta-wedge100/recipes-kernel/pwr1014a-mod/`). Its register
  map documents only one address (0x12) being accessed, confirming the part
  was never PMBus-configured on Wedge100/Wedge100S.
